# CinemaTicket

CinemaTicket is a web application for managing cinema tickets. It allows users to view movie tickets, check their availability, mark tickets as sold or available, create new tickets and delete existing tickets.

The project is developed in stages for the Web Technologies course at POLITEHNICA Bucharest.

The application started as a static HTML/CSS mockup, continued with JavaScript data logic and was then migrated to React with Vite.

Stage 6 introduced a REST API using `json-server`. Stage 7 added a controlled form, validation and persistent CRUD operations. Stage 8 added React Router navigation, a ticket-detail page and CSS Modules.

## Data model

The current ticket objects use the following fields:

| Field | Type | Notes |

| --- | --- | --- |

| `id` | number | Unique ticket identifier generated by the server |

| `titlu` | string | Movie title |

| `gata` | boolean | `false` = available, `true` = sold |

| `tip` | string | `standard`, `vip`, `student` |

| `sala` | number | Cinema hall number |

| `ora` | string | Screening time, e.g. `19:30` |

| `loc` | string | Seat, e.g. `A12` |

| `proiectie` | string | `2D`, `3D`, `IMAX` |

The broader CinemaTicket concept also includes films, cinema halls, screenings, customers, employees and tickets. These are conceptual entities; the current React implementation manages a list of ticket objects, not a relational database.

### Sample data used across the stages

The original three tickets were:

1. Avatar — available, Standard, Hall 4, 19:30, A12, 2D.

2. Oppenheimer — sold, VIP, Hall 2, 21:00, B07, IMAX.

3. Dune: Part Two — available, Student, Hall 1, 18:00, C15, 3D.

The initial dataset had **3 tickets, of which 2 were available**.

In Stage 6, two additional tickets were introduced:

4. Interstellar — available, Standard, Hall 3, 20:00, D08, IMAX.

5. Inception — sold, VIP, Hall 5, 22:00, E10, 2D.

The initial Stage 6 API dataset therefore contained **5 tickets, of which 3 were available**.

From Stage 7 onward, users can modify the dataset through the application, so the current ticket count depends on the saved server data.

## Stage 5: Local state and events

Stage 5 made CinemaTicket interactive using React `useState` and event handlers.

Users could change ticket availability, delete tickets and switch between light and dark themes.

### React state

The initial list of tickets was stored using:

```jsx

const [bilete, setBilete] = useState(BILETE_INITIALE);

```

React automatically re-rendered the interface after state changes.

In Stage 6, this initial state was changed to `useState([])` because tickets started loading from the API.

### Ticket status

The `handleToggle(id)` function updated a ticket using `map()` and inverted its `gata` value.

The card styling and available-ticket counter were updated automatically.

### Deleting tickets

The `handleDelete(id)` function removed a selected ticket using `filter()`.

The list was updated without directly mutating the React state.

### Derived counters

The number of available tickets was calculated using:

```jsx

const active = bilete.filter((bilet) => !bilet.gata).length;

```

The counter was derived directly from the ticket list rather than being stored separately.

### Light and dark mode

The theme was managed with `useState`.

The initial preference was determined using:

```javascript

window.matchMedia("(prefers-color-scheme: dark)")

```

The application applied the selected theme through:

```javascript

document.documentElement.dataset.theme

```

The theme button used `aria-pressed` for accessibility.

### Stage 5 limitations

Ticket changes were stored only in React state.

Refreshing the page restored the original ticket list.

Persistent server-side changes were introduced in Stage 7.

## Stage 6: Data from a mock API

Stage 6 moved the ticket data from React source code into `frontend/db.json` and loaded it through a local REST API.

The API was implemented using `json-server@0.17.4`.

### API configuration

The server runs on port `3001`.

Endpoint:

`http://localhost:3001/bilete`

The `frontend/package.json` file includes:

```json

"api": "json-server --watch db.json --port 3001"

```

The application uses `VITE_API_URL` to configure the API address.

The default address is:

`http://localhost:3001`

### Fetching ticket data

The `fetchBilete()` function retrieves tickets from the server.

The original Stage 6 implementation was:

```javascript

export const API_URL = import.meta.env.VITE_API_URL ?? "http://localhost:3001";

export async function fetchBilete() {

  const res = await fetch(`${API_URL}/bilete`);

  if (!res.ok) {

    throw new Error(`Eroare server: ${res.status}`);

  }

  return res.json();

}

```

In Stage 7, this implementation was expanded with the common `request()` helper and additional CRUD functions.

### React useEffect

The application uses `useEffect` to load ticket data when the component mounts.

The ticket list starts empty:

```jsx

const [bilete, setBilete] = useState([]);

```

Loading and error states are handled separately.

The effect cleanup uses an `ignore` flag to avoid state updates after cleanup.

### Application states

Three situations are handled:

1. Loading — displays a loading message.

2. Success — displays tickets.

3. Error — displays a message if loading fails.

### Stage 6 limitations

Ticket status changes and deletions were still local to React state.

Refreshing the page loaded the original API data.

Persistent modifications were implemented in Stage 7.

## Stage 7: Form and validation

Stage 7 extends CinemaTicket with a controlled React form, input validation and persistent CRUD operations.

Users can create cinema tickets directly from the application without editing `db.json`.

Adding, updating and deleting tickets now use the REST API.

The central rule is:

**First the server confirms the operation, then React state is updated.**

### 7.1. Controlled form

A new component was created:

`frontend/src/components/BiletForm.jsx`

The form contains the following fields:

- Movie title (`titlu`).

- Ticket type (`tip`).

- Cinema hall (`sala`).

- Screening time (`ora`).

- Seat (`loc`).

- Screening format (`proiectie`).

All fields are controlled using React `useState`, `value` and `onChange`.

The form uses `e.preventDefault()` to prevent page reload on submission.

New tickets are created with `gata: false`.

Implementation:

[BiletForm.jsx – Stage 7](https://github.com/sebiandrei12/CinemaTicket/blob/c45fabe/frontend/src/components/BiletForm.jsx)

### 7.2. Input validation

The form validates all submitted data before making an HTTP request.

Validation rules:

- The movie title cannot be empty.

- The title has a maximum length of 100 characters.

- The ticket type must be `standard`, `vip` or `student`.

- The hall must be an integer between 1 and 20.

- The screening time must be in valid `HH:MM` format.

- The seat must follow a format such as `A12` or `B07`.

- The screening type must be `2D`, `3D` or `IMAX`.

When invalid input is detected, the form displays an error message directly on the page.

No browser `alert()` is used.

The title input uses `aria-invalid` to indicate validation errors.

Validation is performed before calling the API.

### 7.3. Preventing duplicate submissions

The form uses a submission state variable named `trimite`.

When a POST request is in progress:

- The submit button is disabled.

- The button displays `Se salvează...`.

- Additional submissions are prevented.

Form fields are cleared only after the server confirms successful creation.

If the API request fails, the values remain available for another attempt.

Implementation:

[BiletForm.jsx – submission handling](https://github.com/sebiandrei12/CinemaTicket/blob/c45fabe/frontend/src/components/BiletForm.jsx)

### 7.4. API implementation

All HTTP requests are centralized in:

`frontend/src/api.js`

A reusable `request()` function handles:

- Fetch requests.

- JSON headers.

- HTTP status verification.

- Response parsing.

- HTTP 204 responses without a body.

Functions implemented:

```javascript

fetchBilete()

createBilet(bilet)

updateBilet(id, changes)

deleteBilet(id)

```

### CRUD operations

| Operation | HTTP method | Endpoint | Function |

| --- | --- | --- | --- |

| Read tickets | GET | `/bilete` | `fetchBilete()` |

| Create ticket | POST | `/bilete` | `createBilet(bilet)` |

| Update ticket | PATCH | `/bilete/:id` | `updateBilet(id, changes)` |

| Delete ticket | DELETE | `/bilete/:id` | `deleteBilet(id)` |

Implementation:

[api.js – Stage 7](https://github.com/sebiandrei12/CinemaTicket/blob/c45fabe/frontend/src/api.js)

### 7.5. React integration

The CRUD functions are integrated in:

`frontend/src/App.jsx`

Three handlers perform server operations:

- `handleAdd()` creates a ticket using POST.

- `handleToggle()` changes ticket availability using PATCH.

- `handleDelete()` deletes a ticket using DELETE.

On creation, the application uses the ticket object returned by the server.

The server generates the new identifier.

On PATCH, the updated object returned by the server replaces the existing object in React state.

On DELETE, the ticket is removed from React state after the server confirms deletion.

This prevents the UI from displaying changes that have not been saved.

Implementation:

[App.jsx – Stage 7](https://github.com/sebiandrei12/CinemaTicket/blob/c45fabe/frontend/src/App.jsx)

The application keeps the ticket counter synchronized with the current list.

Stage 8: Routing and component styling
Stage 8 introduces client-side navigation with React Router and reorganizes the interface into dedicated pages and CSS Modules, while preserving the persistent CRUD functionality of Stage 7.
8.1. Routes and shared layout
frontend/src/main.jsx wraps the application in BrowserRouter. The route map in frontend/src/App.jsx uses a shared Layout component with NavLink, Outlet, and the light/dark theme toggle.
Route	Component	Purpose
/	BiletePage.jsx	Ticket form, list, counter and CRUD operations
/bilete/:id	BiletDetaliuPage.jsx	Individual ticket details
/despre	DesprePage.jsx	Application information
*	NotFoundPage.jsx	Application-level 404 page


The main navigation has data-testid="nav". The / NavLink uses the end prop to avoid also matching ticket-detail URLs.
8.2. Dynamic ticket details
TicketCard.jsx links each movie title to /bilete/${bilet.id} using Link with data-testid="item-link" (replacing the former item-title selector).

BiletDetaliuPage.jsx reads the ID using useParams() and loads the ticket using fetchBilet(id) from frontend/src/api.js. The API makes a GET request to /bilete/:id and checks HTTP errors.

A valid ticket displays its title, type, hall, screening time, seat, projection type, status and ID. The page exposes data-testid="detail" and data-testid="detail-title".

Loading is represented by data-testid="loading". An unknown ticket ID, such as /bilete/999, displays an API error with data-testid="error" and a link to the ticket list.

Unknown application paths, such as /ceva, render the dedicated 404 page with data-testid="not-found".
8.3. CSS Modules
Shared global variables, theme styles and common classes live in frontend/src/index.css. Page and component styles are isolated in:
- components/Layout.module.css
- components/BiletForm.module.css
- components/TicketCard.module.css
- components/TicketList.module.css
- pages/BiletePage.module.css
- pages/BiletDetaliuPage.module.css
- pages/DesprePage.module.css
- pages/NotFoundPage.module.css
Component JSX imports the relevant module and uses styles.className. The application preserves its responsive layout, light/dark themes, ticket-type badges and sold-ticket styling.

## How to run

### Stages 1 and 2: Static mockup

Open `mockup/index.html` using Live Server or directly in the browser.

Use the browser developer tools to inspect the JavaScript console tests.

### Stages 3–8: React application

Open a terminal in the project root and execute:

```bash

cd frontend

npm install

```

For a clean installation based on `package-lock.json`, use:

```bash

npm ci

```

### Start the API

In the first terminal:

```bash

npm run api

```

API endpoint:

`http://localhost:3001/bilete`

### Start the React frontend

In a second terminal, from the `frontend` directory:

```bash

npm run dev

```

Open the local address displayed by Vite, usually:

`http://localhost:5173/`

Both servers must be running for the application to communicate with the local API.

### Production build

From the `frontend` directory:

```bash

npm run build

```

The Stage 7 production build was completed successfully using Vite 8.3.4.

Generated directories such as `node_modules/` and `dist/` should not be committed.
